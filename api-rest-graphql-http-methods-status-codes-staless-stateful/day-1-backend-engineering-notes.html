Day 1 Backend Engineering Notes

1. What is an API?

Definition

An API (Application Programming Interface) is a contract that enables communication between different software systems through predefined request and response formats.

Why APIs Exist

APIs act as a bridge between clients and servers.

Without APIs:

Frontend → Database

Problems:

  • Security risks
  • No validation
  • No authorization
  • No business logic

With APIs:

Frontend
    ↓
API
    ↓
Backend
    ↓
Database

API Request Flow

Client
   ↓
HTTP Request
   ↓
API Endpoint
   ↓
Business Logic
   ↓
Database
   ↓
Response
   ↓
Client

API Contract

An API contract defines:

  • Endpoint
  • HTTP Method
  • Request Format
  • Response Format

Example:

GET /api/clubs/123

Response:

{
  "clubName": "Coding Club"
}

The client depends on the contract, not the backend implementation.

Key Terms

  • Client
  • Server
  • Endpoint
  • Request
  • Response
  • Business Logic
  • API Contract

2. REST vs GraphQL

REST

REST (Representational State Transfer) is an architectural style for designing APIs.

Resources are exposed through URLs and accessed using HTTP methods.

Example:

GET /clubs
GET /clubs/123
POST /clubs
DELETE /clubs/123

Characteristics of REST

  • Multiple endpoints
  • Resource-based URLs
  • Uses standard HTTP methods
  • Stateless communication
  • Simpler to implement

Over-Fetching

Receiving more data than required.

Example:

Needed:

{
  "username": "santhosh"
}

Received:

{
  "username": "santhosh",
  "email": "...",
  "phone": "...",
  "address": "..."
}

Under-Fetching

A single endpoint doesn't provide enough data, requiring multiple API calls.

Example:

GET /user/1
GET /user/1/posts
GET /user/1/followers

GraphQL

GraphQL is a query language for APIs that allows clients to request exactly the fields they need.

Example Query:

{
  user(id: 1) {
    username
    followers
  }
}

Response:

{
  "data": {
    "user": {
      "username": "santhosh",
      "followers": 1000
    }
  }
}

REST vs GraphQL

REST GraphQL
Multiple endpoints Usually one endpoint
Server defines response structure Client chooses fields
Can over-fetch Reduces over-fetching
Can under-fetch Reduces under-fetching
Easier to implement More flexible

Key Difference

REST defines fixed responses.

GraphQL allows clients to select required fields.

3. HTTP Methods

HTTP methods define the action to perform on a resource.

GET

Purpose:

Retrieve data.

Example:

Properties:

  • Read-only
  • Safe
  • Idempotent

POST

Purpose:

Create a new resource.

Example:

POST /clubs

Properties:

  • Creates new resources
  • Not idempotent

PUT

Purpose:

Replace an entire resource.

Example:

PUT /clubs/101

Properties:

  • Replaces complete resource
  • Idempotent

PATCH

Purpose:

Update specific fields.

Example:

PATCH /clubs/101

Properties:

  • Partial updates
  • May be idempotent depending on implementation

DELETE

Purpose:

Remove a resource.

Example:

DELETE /clubs/101

Properties:

  • Deletes resource
  • Idempotent

Methods that do not modify server state.

State

Example:

A stateless API does not store client-specific state between requests.

1. What is an API?

Q1. What is an API?

Answer:

An API (Application Programming Interface) is a contract that allows different software systems to communicate with each other. A client sends a request to an API endpoint, and the server processes the request and returns a response.

Q2. Why do we need APIs?

Answer:

APIs provide a secure and structured way for clients to interact with backend services. They help separate the frontend from the backend and allow validation, authentication, authorization, and business logic to be applied before accessing data.

Q3. What is an API endpoint?

Answer:

An endpoint is a specific URL through which a client accesses a resource or service.

Example:

GET /api/users/101

Here /api/users/101 is the endpoint.

Q4. What is an API contract?

Answer:

An API contract is the agreement between the client and server that defines the endpoint, HTTP method, request format, and response structure that both sides must follow.

Q5. Can two backend services communicate using APIs?

Answer:

Yes. APIs are not limited to frontend-backend communication. Backend services can also communicate with each other through APIs.

Q6. Why shouldn't the frontend access the database directly?

Answer:

Direct database access exposes credentials and creates security risks. The backend API acts as a controlled layer where validation, authentication, authorization, and business rules can be enforced.

Q7. What happens internally when an API is called?

Answer:

The client sends an HTTP request to an API endpoint. The backend processes the request, executes business logic, interacts with the database if needed, and returns a response to the client.

Q8. What formats can APIs return?

Answer:

APIs can return JSON, XML, HTML, images, or files. JSON is the most commonly used format in modern applications.

Q9. Is an API the same as a REST API?

Answer:

No. API is a general concept for communication between systems. REST API is one specific way of designing APIs.

Q10. What are the main components of an API request?

Answer:

An API request typically consists of an endpoint, HTTP method, headers, query parameters, request body, and authentication information.

2. REST vs GraphQL

Q1. What is REST?

Answer:

REST is an architectural style for designing APIs where resources are accessed through URLs and standard HTTP methods such as GET, POST, PUT, and DELETE.

Q2. What is GraphQL?

Answer:

GraphQL is a query language for APIs that allows clients to request exactly the data they need from the server.

Q3. What is the main difference between REST and GraphQL?

Answer:

In REST, the server defines the response structure through predefined endpoints. In GraphQL, the client specifies exactly which fields it wants to receive.

Q4. What is over-fetching?

Answer:

Over-fetching occurs when the server returns more data than the client actually needs.

Q5. What is under-fetching?

Answer:

Under-fetching occurs when a client must make multiple API requests to gather all the required data.

Q6. Why does GraphQL reduce over-fetching?

Answer:

GraphQL allows clients to request only the required fields, so unnecessary data is not included in the response.

Q7. Why does GraphQL reduce under-fetching?

Answer:

GraphQL allows related data to be fetched in a single query, reducing the need for multiple API requests.

Q8. Why is REST easier to maintain?

Answer:

REST uses predictable URLs and predefined responses, making APIs simpler to understand, test, and maintain.

Q9. When would you choose REST?

Answer:

REST is a good choice when data requirements are predictable and simplicity is preferred.

Q10. When would you choose GraphQL?

Answer:

GraphQL is useful when different clients require different subsets of data or when minimizing API requests is important.

3. HTTP Methods

Q1. What is the purpose of HTTP methods?

Answer:

HTTP methods indicate the action a client wants to perform on a resource, such as reading, creating, updating, or deleting data.

Q2. What is GET used for?

Answer:

GET is used to retrieve data from the server without modifying it.

Q3. What is POST used for?

Answer:

POST is used to create new resources on the server.

Q4. What is PUT used for?

Answer:

PUT is used to replace an entire resource with new data.

Q5. What is PATCH used for?

Answer:

PATCH is used to update only specific fields of an existing resource.

Q6. What is DELETE used for?

Answer:

DELETE is used to remove a resource from the server.

Q7. What is the difference between PUT and PATCH?

Answer:

PUT replaces the complete resource, whereas PATCH updates only selected fields.

Q8. Why should GET not modify data?

Answer:

GET is designed to be a safe, read-only operation. Browsers, caches, and crawlers assume GET requests do not change server state.

Q9. What is an idempotent method?

Answer:

An idempotent method produces the same final result even if the same request is sent multiple times.

Q10. Which HTTP methods are idempotent?

Answer:

GET, PUT, and DELETE are generally idempotent. POST is not idempotent because it can create new resources each time it is called.

4. HTTP Status Codes

Q1. Why do we use HTTP status codes?

Answer:

HTTP status codes inform the client about the outcome of a request and whether it was successful or failed.

Q2. What does 200 OK mean?

Answer:

200 OK indicates that the request was processed successfully.

Q3. What does 201 Created mean?

Answer:

201 Created indicates that a new resource was successfully created.

Q4. What does 400 Bad Request mean?

Answer:

400 Bad Request indicates that the client sent invalid or malformed data.

Q5. What does 401 Unauthorized mean?

Answer:

401 Unauthorized means the user has not been authenticated or provided valid credentials.

Q6. What does 403 Forbidden mean?

Answer:

403 Forbidden means the user is authenticated but does not have permission to access the resource.

Q7. Difference between 401 and 403?

Answer:

401 is an authentication issue, while 403 is an authorization issue.

Q8. What does 404 Not Found mean?

Answer:

404 Not Found indicates that the requested resource does not exist on the server.

Q9. What does 409 Conflict mean?

Answer:

409 Conflict indicates that the request conflicts with the current state of the system, such as creating a duplicate email.

Q10. What does 500 Internal Server Error mean?

Answer:

500 Internal Server Error indicates an unexpected problem occurred on the server while processing the request.

5. Stateless vs Stateful APIs

Q1. What is state?

Answer:

State is information remembered about previous interactions that can be used while processing future requests.

Q2. What is a stateful API?

Answer:

A stateful API stores client-specific information on the server between requests.

Q3. What is a stateless API?

Answer:

A stateless API does not store client-specific information between requests. Each request contains all information needed for processing.

Q4. Why is session authentication stateful?

Answer:

Session authentication is stateful because the server stores session information and uses it to identify users in future requests.

Q5. Why is JWT authentication stateless?

Answer:

JWT authentication is stateless because the server does not store session data. The client sends the token with every request.

Q6. Why are REST APIs considered stateless?

Answer:

REST requires each request to contain all information necessary for processing, making requests independent of one another.

Q7. Why are stateless APIs easier to scale?

Answer:

Stateless APIs allow any server instance to process a request because no session data is stored on a specific server.

Q8. What is a sticky session?

Answer:

A sticky session ensures that requests from a user are always routed to the same server instance that holds their session data.

Q9. What is a session store?

Answer:

A session store is a centralized storage system used to maintain session data across multiple servers.

Q10. What is the main difference between session-based authentication and JWT authentication?

Answer:

Session-based authentication stores user state on the server, whereas JWT authentication stores authentication information in a token sent with each request.
